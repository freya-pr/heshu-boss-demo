## 1. 重构到 1.0 的核心价值

### 1.1 建立可信的统一客户身份

以合数BOSS客户编码作为内部客户主键，以手机号、UnionID、企业微信外部联系人等作为身份标识，解决不同渠道、不同员工和新旧系统之间的客户重复、身份冲突及档案割裂问题。

1.0 后，合数BOSS成为客户身份、客户编码、当前负责人、协作关系和归属裁决的主系统。

### 1.2 把“线索到客户”从人工经验变成标准流程

将渠道导入、线索分配、员工活码、扫码加微、SOP、问卷、客户定级和转客户串成可配置、可追踪、可度量的业务闭环，减少线索丢失、重复跟进和人工对账。

### 1.3 降低历史 SCRM 的耦合和改造风险

不再继续把所有业务堆叠到历史 SCRM。合数BOSS独立承接客户关系主链路，旧 SCRM 在过渡期保留旧活码、直播、内容及尚未迁移的运营能力，通过接口与事件协作。

### 1.4 形成可治理的客户归属机制

V1.0 通过分配规则明确客户为什么分给某个员工，并通过撞单管理完成强身份冲突阻断、证据核验、人工裁决和反向恢复。公海和商机能力已取消；离职继承不属于当前版本，存量负责人调整通过业务页面人工改派完成。

### 1.5 沉淀可持续扩展的数据底座

统一线索、客户、身份、负责人、标签、问卷、等级、跟进和事件模型，为后续订单、售后、直播、课程及 AI 分析提供稳定客户主数据，避免后续模块再次重复造客户档案。

### 1.6 让经营指标真正可计算

统一线索数、分配数、扫码数、加微数、问卷数、定级数和转客户数的统计口径，形成可以按渠道、员工、部门和时间回溯的转化漏斗。

## 2. 1.0 的定义

1.0 不代表历史 SCRM 全部功能完成迁移，而代表：

1. 一转部门能够以合数BOSS作为线索和客户管理主入口；
2. 新增线索能够在合数BOSS完成从接入到唯一客户的闭环；
3. 新员工活码统一由合数BOSS创建，旧 SCRM 活码产生的数据能够同步进入合数BOSS；
4. 手机号或 UnionID 任一有效身份可以创建或关联唯一客户；
5. 身份冲突能够被原子阻断、自动创建唯一撞单案件，并在线完成证据核验、指定主档合并或确认不同人；
6. 已收集问卷能够关联客户并按已发布规则生成 S/A/B/C 等级；
7. 客户档案、标签、跟进、人工改派及基础分析可支持一转日常业务；
8. 历史客户完成试迁移、全量迁移和对账，关键差异有明确处理结论；
9. 统一登录、权限、审计、监控、异常补偿和回滚方案通过验证；
10. 完成一个真实团队灰度，关键指标稳定后才允许扩大使用范围。

以下内容不作为 1.0 上线门禁：

- 历史 SCRM 全部下线；
- 直播、内容、订单、售后、营期和班级全部迁移；
- 自动抓取全部聊天记录；
- 复杂销售预测和 AI 能力；
- 多企业微信 CorpID；
- 所有第三方系统一次性接入。

## 3. 版本里程碑

> 版本时间允许部分并行，但每个版本必须满足自身门禁后才能合并进入 1.0 发布候选版本。

| 版本 | 计划时间 | 业务目标 | 主要交付 | 进入下一阶段门禁 |
|---|---|---|---|---|
| V0.1 范围与底座 | 2026-08-20—2026-09-14 | 固定 1.0 边界并搭好可持续开发底座 | [合数BOSS系统管理1.0 PRD](./合数BOSS V1.0系统管理与业务配置需求文档.md)、PRD、原型、统一登录接入、组织员工映射、合数BOSS角色菜单、应用壳、基础字典、日志追踪 | 首期主链路、系统边界、数据责任人和接口责任人签字确认；核心数据模型评审通过 |
| 项目正式启动 | 2026-09-15（T0） | 启动基线转为正式执行计划 | 启动会纪要、正式团队名单、8 周排期、风险和依赖清单 | 资源、环境和外部接口条件到位，项目决策机制生效 |
| V0.2 客户身份基础 | 第 1—2 周 | 建立线索、客户和身份主模型 | 客户编码、手机号/UnionID 身份、查重服务、幂等、冲突记录、导入框架 | 单身份和双身份查重用例通过；并发创建不产生重复客户；冲突不自动覆盖 |
| V0.3 线索接入与分配 | 第 2—3 周 | 让线索进入合数BOSS并明确负责人 | 线索列表、人工/批量导入、IDMS 接口、组织到人式人工指定、活码排班规则、接量权重、分配历史 | 不丢线索；重复导入可识别；分配结果可解释；失败进入人工队列 |
| V0.4 活码与加微闭环 | 第 3—4 周 | 让线索获得活码并完成扫码加微 | 合数BOSS活码、旧 SCRM 活码事件接入、企微回调、全天/分时段接待及全天兜底、扫码及加微关系 | 新旧活码事件均能关联原线索；重复/乱序回调幂等；员工停用后不再接待 |
| V0.5 客户生成与撞单裁决 | 第 3—5 周 | 从加微关系形成可信唯一客户 | 自动转客户、客户档案、身份补录、身份冲突检测、撞单建案、证据核验和线上裁决 | 手机号或 UnionID 任一身份可转客户；冲突不自动覆盖；撞单可领取、裁决、审计和反向恢复 |

| V0.9 发布候选版 | 第 7 周 | 达到可灰度状态 | 全链路回归、权限、安全、性能、容量、监控、告警、备份恢复和回滚演练 | P0/P1 缺陷清零；关键性能达标；回滚演练通过；产品、测试、技术同意灰度 |

| V1.0 正式版本 | 第 8 周末，预计 2026-11-10 左右 | 合数BOSS成为一转线索与客户主入口 | 1.0 制品、迁移报告、操作手册、监控看板、应急预案、培训和切换公告 | 发布委员会确认；旧链路保留受控回退能力；关键数据完成发布前后对账 |

## 4. 并行实施建议

基于技术 7 人、测试 2 人、产品 1 人，建议按三个交付流并行：

| 交付流 | 建议投入 | 负责范围 |
|---|---:|---|
| 客户领域主链路 | 3 名技术 | 线索、分配、客户身份、转客户、撞单、客户档案 |
| 外部集成与数据 | 2 名技术 | 企业微信、活码、旧 SCRM、IDMS、句子系统、迁移和对账 |
| 平台与运营能力 | 2 名技术 | 登录权限、标签、跟进、改派、报表、监控 |
| 测试保障 | 2 名测试 | 1 人侧重接口、数据和自动化；1 人侧重业务、权限和端到端 |
| 产品统筹 | 1 名产品 | 范围、原型、口径、业务确认、验收组织和变更控制 |

产品和测试不应等开发结束后再介入。V0.2 起测试同步编写接口、幂等、权限和数据对账用例；每个版本结束前产品组织业务走查。

## 5. 各阶段共同门禁

每个版本只有同时满足以下条件才可标记完成：

- 范围内页面、接口、事件、数据模型及权限全部实现；
- 正常、空数据、异常、无权限、重复提交和并发场景通过；
- 核心写操作具备幂等、审计、监控和补偿机制；
- 需求、设计、架构、接口、数据字典和测试文档同步更新；
- 数据变更可以按批次、事件或审计记录识别影响范围；
- 已写清楚发布判断、止损阈值和回滚动作；
- 产品、测试、技术及对应业务验收人给出明确结论。

## 6. 1.0 上线关键指标

上线前确定基线和目标值，至少监控：

| 指标 | 1.0 判断方向 |
|---|---|
| 线索接入成功率 | 不低于 99.9%，失败可查询、重试和补偿 |
| 自动/人工分配成功率 | 不低于 99.9%，无合格员工时进入人工队列 |
| 企微事件处理成功率 | 不低于 99.9%，重复和乱序事件不产生重复数据 |
| 重复客户生成量 | 唯一约束下不得产生无法解释的重复客户 |
| 错误身份合并量 | 必须为 0 |
| 撞单未处理量与时长 | 超时可升级，所有裁决可追溯 |
| 问卷关联准确率 | 自动关联必须唯一确定，不确定记录进入异常队列 |
| 客户定级可解释率 | 100% 可追溯问卷、规则版本和命中条件 |
| 迁移对账差异 | 核心身份、客户编码和负责人差异必须全部解释 |
| 权限越权事件 | 必须为 0 |
| P0/P1 缺陷 | 上线前必须清零 |

每个阶段进入开发前，须在[迭代验收与回滚](../05-testing/ACCEPTANCE_ROLLBACK.md)中建立对应迭代记录。
