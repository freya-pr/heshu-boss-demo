# 数据字典

状态：待产品、数据和后端共同补齐，是核心开发前置条件。

客户生命周期、客户360°档案域、核心实体关系及家长/孩子对象口径详见 [合数BOSS客户360°档案与生命周期需求](../01-product/合数BOSS客户360档案与生命周期需求文档.md)。

## 首批实体

- 组织、员工、用户、角色、权限和数据范围；
- 应用、菜单、消息、待办和审计；
- 线索、客户、客户身份、负责人、公海记录；
- 活码、跟进、挖需、问卷、答案、定级规则和等级历史；
- 标签、商机、集成事件、导入任务和异常记录。
- 系统参数、参数版本、字典类型和字典项。
- IP主档、IP大类、IP渠道及IP配置；IP编码由管理员必填并全局唯一，大类编码仅作后台稳定值且页面不展示；活码必须通过IP编码关联启用IP并保存渠道编号快照；第三方商品与店铺、活码关联。

每个字段必须记录：中文名、英文名、类型、长度、必填、默认值、枚举、唯一性、脱敏规则、来源系统、主系统及业务说明。

## 系统参数与字典建模补充

- `sys_parameter` 保存参数名称、不可变参数键、类型、分组、参数值/密文引用、敏感标记、状态、说明和版本号；参数键全局唯一；
- 参数类型限定为 `STRING/NUMBER/BOOLEAN/JSON/SECRET`，写入时由服务端按类型校验；敏感值不得通过通用查询、日志和导出返回；
- `sys_dictionary_type` 保存字典名称、不可变字典编码、状态和说明；字典编码全局唯一；
- `sys_dictionary_item` 保存字典类型、不可变项值、可调整显示标签、排序、标签颜色、状态和说明；同一字典内项值唯一；
- 业务数据保存稳定项值，不保存当前中文标签；字典项停用后禁止新选择，但历史值必须继续解析；
- 参数与字典均采用逻辑停用和审计，不对已引用记录执行物理删除；缓存键必须包含配置版本，变更后主动失效。
- IP大类使用字典编码 `ip_category`，初始项为“教育规划”，字典项值 `EDUCATION_PLANNING` 即大类编码；`lead_ip_profile.ip_category` 保存大类编码，`ip_name` 保存老师姓名或老师对外名称（如“阿留皮皮”）。
- IP配置不是独立主数据表，统一维护 `lead_ip_profile` 中IP名称、IP大类编码与IP渠道编号的关系；IP编号位于IP名称下方展示，大类编码位于IP大类下方展示。
- 活码选择IP后只读带出IP渠道；关系记录至少保存 `qr_code_ref`、`ip_no`、`ip_channel_code_snapshot`、生效/失效时间和操作人，禁止在活码侧另行覆盖IP渠道。
- IP渠道引用渠道主数据而非自由文本：初始渠道为“店播/CH000001”“阿留专属/CH000002”；`lead_ip_profile.channel_id/channel_code` 保存渠道内部ID和稳定编号，渠道名称仅用于展示。
- `lead_product` 保存来源平台、第三方商品ID、商品名称、状态、店铺ID、是否存在有效活码关联、首次/最近同步时间和内部备注；第三方商品ID使用字符串类型，唯一匹配按“来源平台/店铺 + 第三方商品ID”处理。
- `lead_ip_product_rel` 保存IP与商品的有效期关系和变更来源；商品或IP停用时不得删除历史关系。

## 线索类型扩展建模补充

- 引流线索与三方品线索共用 `crm_lead` 主模型，公共身份、来源、负责人、分配和状态字段保持一致；V1.0 仅开放引流线索，三方品线索菜单及扩展视图在 V1.5 开放；
- `third_party_product_id` 保存来源平台原始商品ID，使用 `varchar(128)`，允许为空并保持原始字符串；以“来源平台/线索来源 + 第三方商品ID”建立查询索引和业务匹配关系，不单独承担全局唯一性；
- 两类线索分别使用 `crm_lead_drainage_ext`、`crm_lead_third_product_ext` 或等效的版本化扩展结构保存差异字段；
- 稳定且需要筛选、分配、统计的扩展字段必须定义明确列和索引，不允许所有字段无约束写入 JSON；
- 每类扩展记录保存 `schema_version`，列表列、详情区块、导入模板和校验规则按线索类型配置；
- 导入与同步任务作为两类线索页面内的异步操作及任务抽屉，不作为独立业务菜单，但仍需保存批次、进度、失败、重试和对账数据。

## 合数BOSS组织员工建模补充

- 组织树采用可变层级，组织类型至少支持集团、公司、校区、部门和小组；部门可以直接挂员工，也可以下设小组；
- `employee_id` 由合数BOSS生成并作为应用内员工主键，企业微信 UserID 不得直接作为员工主键；
- `employee_no` 由合数BOSS按 `B` + 6 位并发安全流水号生成和维护；旧SCRM员工标识只保存为历史别名，不作为新员工编号来源；
- 使用独立的员工外部身份表记录 `WE_COM_USER_ID` 和历史SCRM员工标识，并包含来源CorpID、状态及生效区间；
- 当前企微绑定采用账号一对多、外部身份全局唯一：一个生效登录账号可绑定多个 `CorpID + UserID`，同一 `CorpID + UserID` 只能绑定一个登录账号；绑定表不对 `account_id` 建立唯一约束，对生效的 `(corp_id, wecom_user_id)` 建立联合唯一约束；
- 旧企微UserID、旧SCRM员工标识和换绑记录进入历史身份表，只用于历史追溯，不参与登录、权限计算或新业务归属；
- 企微基线与现有员工主档疑似同人但无法唯一判断时进入身份冲突表，不得只按姓名自动合并；
- 必须保存来源快照和映射历史，保证旧 SCRM 的企微负责人、活码和操作记录能够追溯到合数BOSS员工。
- 上线基线只使用整改后的企微组织员工数据进入暂存区并经业务确认；未经确认的数据源不得进入员工主档、身份匹配、员工编号或同步对账链路；
- 后续由合数BOSS向企业微信下发变更，企微数据只用于外部 ID、激活/接待状态、同步结果和差异告警，不反向覆盖合数BOSS核心字段；
- 员工任职经历使用独立 `employee_employment_record` 或等效实体记录入职、离职、主组织、岗位、状态和生效区间；重新入职确认是同一自然人时复用原 `employee_id/employee_no` 并新增任职记录；
- 重新入职不得自动恢复历史角色、数据岗位、客户、活码和待办；新任职授权和业务分配使用新的关系记录，历史记录仍关联原员工与实际外部身份；
- 自有系统主控状态使用版本化系统配置保存，至少包含 `master_control_enabled`、当前方向、配置版本、生效时间、操作人、切换原因、快照/游标及在途任务处理结果；禁止仅依赖前端开关状态；
- `master_control_enabled=true` 时只允许合数BOSS向外写主数据；为 `false` 时暂停向外写入并允许外部数据经过暂存、校验和冲突处理后进入合数BOSS；两个方向的消费者不得同时启用；
- 组织小组允许继续嵌套，组织关系使用父节点和路径表达，不以固定层级列建模。
- `sys_wecom_provision_task` 保存唯一请求号、员工ID、账号ID、CorpID、目标UserID、目标企微部门、当前步骤、任务状态、企微错误码、创建/邀请/激活时间、重试次数和审计字段；请求号全局唯一。
- 企微开通状态建议使用 `VALIDATING/LOOKING_UP/CREATING/CREATED_PENDING_INVITE/INVITED_PENDING_ACTIVATION/ACTIVE_BOUND/IDENTITY_CONFLICT/CREATE_FAILED/INVITE_FAILED/RECONCILING`；业务页面不得将 `CREATED_PENDING_INVITE` 显示为已激活。
- 创建企微成员前以手机号和历史外部身份双重查重；拟生成UserID由后端稳定生成并唯一约束，页面不得手工修改；创建成功后持久化当前绑定，邀请失败只重试邀请。

## 合数BOSS支付配置建模补充

- 支付配置与支付配置版本分离，默认支付通过版本化指针切换，不覆盖历史配置；
- 私钥、Secret 和退款凭据不得以可回显明文保存，业务表只保存密钥服务引用、指纹或强单向哈希；
- 同一组织、业务场景和环境只能存在一个有效默认支付配置；
- 默认切换、密钥轮换、退款凭据重置和回滚必须保存独立审计记录；
- 已被支付、退款或回调记录引用的配置只能停用和版本归档，不得物理删除。
