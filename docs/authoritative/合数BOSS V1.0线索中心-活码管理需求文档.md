## 1. 文档定位与边界

本文档是“活码管理”子模块的独立详细需求，可直接用于产品评审、交互核对、开发实现、测试用例编写和验收。本文档完整承接当前总需求中该模块的有效规则；跨模块状态、公共数据口径和发布规则仍与上位基线保持一致。

## 2. 功能详细需求

### 5.6 活码管理

- 新活码统一由合数BOSS创建和管理；
- 旧活码继续使用并保存旧SCRM来源及外部编号映射；
- 页面顶部提供**当前企业微信主体**全局选择区，展示企业名称和企微ID（CorpID）；候选项仅包含当前用户有权使用且处于已授权状态的企业微信主体；
- 默认选中用户上次使用的有效企微ID；无历史记录时选择第一个有权使用的主体。切换企微ID后，活码统计、分组数量、活码列表、筛选结果以及新建活码候选数据按所选主体整体刷新，不混合展示不同主体数据；
- 新建活码自动绑定当前选中的企业微信主体和企微ID，并保存 `corp_id`、主体名称快照及创建时授权关系；既有活码不允许通过普通编辑切换企微ID，避免扫码链接、员工范围、企微标签和历史事件跨主体错绑；
- 页面左侧提供**活码分组**，默认包含“全部活码”和“默认分组”，管理员可新增分组；自定义分组可在“更多”中修改名称或删除，删除后组内活码移入默认分组；默认分组不可删除；点击分组后右侧列表仅展示该分组数据，分组名称完整展示并同步展示活码数量；
- 活码列表支持按活码名称/编号、关联IP名称/编号、IP渠道、员工、所属期次和活码状态查询；展示活码名称与编号、活码分组、关联IP、自动带出的IP渠道、所属期次、接待员工、企微标签、内部标签、创建人、创建日期、扫码/加微数据和状态，不展示二维码、活码类型、接量日期或容量字段；
- 新增和编辑活码必须关联一个启用IP。未选择时阻断保存并提示“请选择关联IP”；选择后系统从IP主档自动带出只读的IP渠道名称与渠道编号，不允许在活码中另行选择或覆盖；
- **所属期次为选填项**。从“线索中心—引流期次”选择启用期次并支持名称搜索，不允许自由填写；不选择时按通用活码保存，不限定引流期次；
- 活码统一按多人接待配置，不展示活码类型；支持自动通过好友开关、全天在线/分时段排班以及轮询/顺序/随机分配；新分配请求统一按当前有效排班及分配方式选人，不因历史接待关系优先指定员工。同一请求的重试仍返回已保存结果，不重复分配；
- 选择全天在线时，在“排班设置”下方展示独立“接待员工”区，选择员工后直接配置每人的接量权重并只读展示当前接量；
- 选择分时段排班时，先展示“自定义分时段规则”，再展示“全天在线兜底”。固定说明为“自定义分时段规则说明：选择分时段排班时，默认需要一条全天在线规则，不可删除，保证有员工全天在线”；“添加规则”位于自定义规则标题旁；
- 每条自定义规则直接选择员工、工作日和在线时间，选中员工后在规则内直接配置接量权重并只读展示当前接量，不再单独配置接待员工；自定义规则至少保留一条；
- 全天在线兜底固定覆盖周一至周日 00:00—23:59 且不可删除，兜底人员直接在该规则内修改并配置接量权重，至少一人；自定义规则与兜底规则的员工自动汇总为活码接待员工；
- 活码标签分为**企微标签**和**内部标签**。企微标签在扫码加微成功后同步写入企业微信；内部标签仅用于合数BOSS内部筛选、运营和数据分析，两类标签分别存储、分别展示，不允许混用；
- 列表支持查看详情、编辑和启停，不提供下载活码或复制短链入口；详情不展示二维码，也不提供下载活码按钮；
- 活码详情展示企业微信主体和企微ID；导出、扫码/加微统计及配置审计均携带 `corp_id` 条件；
- 主体切换受岗位数据范围和角色操作权限共同约束；没有可用企微主体时页面显示“暂无已授权企业微信主体”，并禁用新建、编辑、下载和启停操作；
- 员工离职或停用后立即停止新接待；当前命中规则无可用员工时进入待配置异常；
- 扫码、加微和删除好友事件按企业微信事件编号幂等保存；
- 活码效果展示扫码数、加微数、有效关联数和异常数，统计口径可追溯。


#### 5.6.1 新建/编辑校验

| 字段 | 必填 | 规则 |
|---|---|---|
| 企业微信主体 / 企微ID | 自动 | 取页面顶部当前选中的已授权主体；新建时写入且不可在普通编辑中变更；所有员工、企微标签及事件接口均按同一 `corp_id` 查询和校验 |
| 活码名称 | 是 | 30字以内；同一有效期次内名称不可重复 |
| 活码分组 | 是 | 从活码分组中选择；新建分组成功后可立即选用；不允许保存到已删除分组 |
| 关联IP | 是 | 从IP管理中搜索IP名称或IP编码；只允许选择启用IP，新增、编辑保存前都必须校验，未选择时阻断保存 |
| IP渠道 | 自动 | 选择IP后按IP配置自动带出渠道名称和稳定渠道编号；只读，不允许单独修改 |
| 所属期次 | 否 | 从启用的引流期次中选择，保存期次ID和名称快照；不选择时按通用活码保存 |
| 排班类型 | 是 | 全天在线、分时段排班 |
| 排班方式 | 是 | 轮询、顺序、随机 |
| 接待员工 | 全天在线时必填 | 至少一名在职启用员工；选择后直接配置接量权重，当前接量只读 |
| 自定义分时段规则 | 分时段时必填 | 至少保留一条；每条规则至少选择一名员工、一个工作日和有效时间范围；员工在规则内直接配置接量权重 |
| 全天在线兜底 | 分时段时必填 | 系统默认生成且不可删除，固定周一至周日 00:00—23:59；至少选择一名兜底员工并在规则内配置接量权重 |
| 企微标签 | 否 | 扫码加微成功后同步写入企业微信客户标签，保存企微标签ID和名称快照 |
| 内部标签 | 否 | 仅写入合数BOSS内部标签体系，保存内部标签ID和名称快照 |

新增/编辑页面按“基础信息—排班设置—接待员工（仅全天在线）—客户标记”排列；分时段模式的人员和权重均在各排班规则内完成。

#### 5.6.2 状态和审计

- 状态包括启用和停用，不再根据接量日期计算待生效或已结束；
- 活码启停、所属期次、排班类型、排班方式、规则时段、员工名单和接量权重修改必须记录修改前后值、操作人和时间；
- 企微ID切换记录用户、切换前后 `corp_id` 和时间；切换只改变当前页面查询上下文，不改写任何既有活码归属；
- 关联IP变更必须记录原IP、新IP、变更时渠道编号快照、操作人和时间；IP主档后续改渠道不得静默改写既有扫码和线索的历史归因快照；
- 活码记录必须保存创建人ID、创建人姓名和创建时间；创建人名称变化不覆盖历史名称快照；
- 分组新增、活码移组、企微标签和内部标签变更均进入配置变更记录；
- 已产生扫码或加微数据的活码禁止物理删除，只允许停用；
- 详情页展示基础信息、员工接量明细、扫码/加微数据及配置变更记录。


#### 5.6.3 活码详情字段实际说明

详情是当前活码配置及运行结果的只读视图，不等于客户档案，不提供二维码及下载入口。以下“现有”指当前原型源码已展示，不代表真实接口已接通；“待补”指详情尚未完整展示。打开详情仍需校验活码所属主体和操作者数据权限，不能仅依赖列表筛选。

| 区域 / 字段 | 业务含义及来源 | 展示、空值与变更说明 | 原型状态 |
|---|---|---|---|
| 活码名称、活码编号 | 名称用于运营识别；编号用于稳定定位活码，不是员工编号或企微ID | 名称可编辑；编号不可编辑。旧码需另保留来源系统及外部编号映射 | 现有；旧码映射待补 |
| 状态 | 管理员对新接待入口的启停控制 | 仅启用/停用；启用不代表当前必有可用员工，不恢复接量日期状态 | 现有；旧模拟记录仍需清理 |
| 企业微信主体、企微ID | 当前活码绑定企业名称及 `corp_id` | 普通编辑不可变更；是员工、标签、事件及授权校验边界，不是客户身份 | 现有 |
| 活码分组 | 同一主体内的运营分类 | 默认分组兜底；移组只改变分类，不改历史归因和负责人 | 现有 |
| 创建人、创建时间 | 创建操作的人员及时间快照 | 创建人姓名变化不回写历史；系统迁移需标明来源；缺失展示“未记录”，不补造 | 创建人现有；创建时间详情待补 |
| 关联IP、IP编码 | 此活码必填的IP归因配置 | 新增、编辑不允许留空；不凭活码名称猜IP；变更仅影响后续归因 | 现有 |
| IP渠道、渠道编号 | 从关联IP带出的只读渠道关系 | 无关系显示“未配置”；详情当前值与历史事件快照分开，不重算历史 | 现有 |
| 所属期次 | 引流期次主档的业务归属，不是活码使用期限 | 未选显示“未关联（通用活码）”；关联期次不自动生成开始/结束状态 | 现有 |
| 自动通过好友 | 是否请求企微按支持的能力免去人工通过步骤 | 展示开启/关闭；开启不等于已加微，仍以真实成功事件或同步事实为准 | 现有 |
| 排班类型、排班方式 | 前者决定当前候选员工，后者决定候选集内如何选人 | 分别展示全天在线/分时段排班与轮询/顺序/随机，不能混成同一概念 | 现有 |
| 每条时段规则 | 规则编号、工作日、开始/结束时间、配置员工及各自权重 | 展示全部规则，不得仅展示第一条；当前是否命中属于计算结果，须标明计算时间 | 完整规则待补 |
| 全天在线兜底 | 分时段模式的固定兜底规则及人员 | 不可删除，至少一人；有名单不等于人员当前可用；启用条件见 5.6.4 建议 | 单独展示待补 |
| 企微标签、内部标签 | 加微后对外同步的企微标签与BOSS内使用的标签分别存储 | 无标签显示“未配置”；详情展示配置，不代表标签同步已经成功；不新增人工标签创建入口 | 现有 |
| 接待员工姓名、员工编号、岗位 | 接待人员的主档展示信息 | 以内部员工ID关联，企微UserID仅作同主体映射；汇总名单去重，不代表全员此刻在线 | 现有 |
| 接量权重 | 员工参与加权轮询的相对比例 | 不是最多可接人数，不用“当前接量/权重”计算剩余额度；配置作用域见 5.6.5 | 现有，原型以 `limit` 暂存 |
| 当前接量 | 员工实际接待分配的数量指标 | 只读；必须标明统计范围、截止时间及是否含改派；当前模拟数尚无真实口径 | 现有模拟值；建议见 5.6.6 |
| 扫码数、加微数 | 入口事件与加微成功事件的不同统计 | 不能以一次分配同时增加两项；无事件能力显示“暂不可统计”，有能力但无事件显示0 | 现有模拟值 |
| 有效关联数、异常数 | 成功关联线索/客户的结果及运行异常 | 现有需求已提及，但需分别显示对象与去重口径，不能用加微数代替 | 待补 |
| 配置变更记录 | 变更前后值、操作人、时间及配置版本 | 只追加，支持追溯执行时配置；不能用当前配置解释全部历史分配 | 待补 |

#### 5.6.4 基于活码的分配链路（细化建议待确认）

现有确定边界：活码按主体隔离；员工必须在职且启用；自动分配受排班名单约束；轮询使用权重而非容量；人工指定不受排班与权重约束。下表补足未明确的执行顺序，评审通过后再实现。

| 步骤 | 建议执行逻辑 | 未满足时的处理 |
|---|---|---|
| 1. 区分入口 | 扫码请求按入口携带的活码ID定位；后台批量轮询按线索及已发布规则定位活码。人工指定是独立流程，不伪装为自动轮询 | 请求缺少主体或来源标识时记异常，不任选活码 |
| 2. 确定唯一活码 | 显式绑定优先；无显式绑定时按已发布规则的优先级及期次/IP条件唯一匹配；通用活码仅在规则明确允许兜底时使用 | 同优先级多码冲突、无匹配或显式绑定已停用，均停止该条任务；不按创建时间随意选“最新一个” |
| 3. 校验可服务条件 | 校验主体授权、活码启用、请求对象可操作及当前配置版本；旧码须通过来源映射得到唯一活码 | 主体失效或停用阻断新接待，保留历史数据和已发生事件 |
| 4. 命中排班 | 全天在线取独立接待名单；分时段优先匹配当前工作日及时段。**已确认：命中自定义时段但过滤后无人可接待时，自动转给全天兜底人员。**未命中任何时段时使用兜底仍为建议待确认 | 兜底也无人可用则待分配，不从其他主体或任意员工补人 |
| 5. 过滤人员 | 只保留当前规则内在职、账号启用、具有本主体有效企微映射及接待资格的员工，按内部员工ID去重 | 保留排除原因；不能通过增加权重恢复离职、停用员工资格 |
| 6. 选择员工 | 按当前排班方式选出一个员工；记录候选集、排除原因、权重及算法版本，不设置历史接待员工优先分支 | 不可用或并发失效时有限重试，仍失败转异常，不无限循环 |
| 7. 提交分配 | 已有线索写入负责人、组织及分配快照；匿名扫码先保存接待选择记录，不凭匿名访问创建正式客户。响应返回前持久保存幂等结果 | 同一请求重试返回原结果；分配冲突不能覆盖已确认人工改派 |
| 8. 承接加微 | 返回实际可用的接待入口；以后续企微事件关联真实客户及员工关系，再执行标签同步与归因 | 分配成功但未加微是正常中间状态；加微与标签失败分别处理 |

时间规则建议：统一使用 Asia/Shanghai 服务端时间；时段按“含开始、不含结束”判断，全天覆盖至次日00:00（页面23:59仅表示全天）。跨午夜拆为两条工作日规则；同一活码的自定义规则重叠时禁止保存并指出冲突，避免隐式合并权重。以上时间及重叠策略需产品确认，当前原型未完整校验。

“全天兜底”建议只在没有可用自定义时段名单时参与，不能常驻混入每条时段名单，否则运营设置的白班比例会被兜底人员稀释。活码接待选择不自动改写客户中心主负责人或其他员工的企微跟进关系。

#### 5.6.5 三种分配方式与权重（算法建议待确认）

| 方式 | 建议业务定义 | 权重及当前接量的关系 |
|---|---|---|
| 轮询 | 采用平滑加权轮询；候选A/B/C权重为2/1/1时，稳定候选集下长期接量约为50%/25%/25% | 权重影响比例，不是上限；不要求任意短窗口绝对相等 |
| 顺序 | 每次从配置顺序首位查找可用员工，首位不可用才尝试下一位 | 不使用权重；由于没有容量上限，首位持续可用时会持续接待，必须向运营提示，不得误称平均分配 |
| 随机 | 在当前可用候选集中等概率选择一人，并持久保存本次结果 | 建议不使用权重；如需加权随机须另行确认，不能与加权轮询混用 |

权重建议按“活码ID＋排班规则ID＋员工ID”独立保存，整数1—999、默认1；原型控件范围已为1—999，但默认值及作用域尚待确认。同一员工可在不同时段及兜底配置不同权重；修改当前规则不得联动其他规则、其他活码，也不得在取消编辑后残留。顺序/随机模式不消费权重，详情应提示“本方式不使用权重”。

研发建议：加权轮询每次将各候选的累计分值加上自身权重，选择最高分者并减去候选权重总和；同分按稳定配置顺序选择。累计分值与成功分配在同一事务或等价原子机制下提交，失败不推进；状态按主体、活码、规则、配置版本隔离。名单/权重变更生成新版本，新版本分值初始化，旧任务仍保留旧快照。初始化会影响短期比例，频繁改权重须在审计中可见。

批量轮询仍按线索页面明确选择的“轮询”动作执行，不静默继承活码“随机/顺序”；两入口可复用候选名单服务，但必须记录实际算法及触发来源。此入口冲突处理为建议待确认，不据此变更原有按钮。

#### 5.6.6 分配、扫码与加微统计（口径建议待确认）

统计均按 `corp_id＋活码ID` 隔离并标记数据截止时间。详情无日期筛选时建议从活码创建起累计；旧码只能从有可靠事件的起点统计，需提示覆盖时间。不能把员工全局数据复制到每个活码。

| 指标 | 建议口径 | 不计入的情况 |
|---|---|---|
| 当前接量 | 本活码下该员工累计成功提交的唯一接待分配记录数，合并各规则去重 | 同一请求重试、选人后提交失败、其他活码接量、独立人工改派 |
| 扫码数 | 去重后的可验证扫码事件次数，不等于人数；无扫码事件来源时不可用页面访问量冒充 | 重复回调；仅生成/下载活码；仅有加微事件而无扫码证据 |
| 加微数 | 建议按本主体、活码、外部联系人、员工的首次成功关系去重；同一人加不同员工属于不同关系 | 自动通过开关开启、分配成功、重复回调；删除后重加同一关系不重复计首次数 |
| 有效关联数 | 建议统计已唯一关联内部客户的接待记录数；若需要线索关联数，独立命名展示 | 匿名未识别、多个候选冲突、重复关联事件 |
| 异常数 | 建议展示当前未关闭异常案件数，另保留累计异常次数 | 同一异常重试不能重复创建案件；已关闭案件不计待处理数 |

上述指标分母不同，扫码数与加微数不能直接保证形成同一批次的转化率；若增加转化率，必须采用同一扫码批次及明确观察窗口，不使用“历史加微数÷当日扫码数”。真实事件无法提供所需关联标识时展示覆盖缺口，不生成推测数据。

#### 5.6.7 配置变更、权限与异常处理补充

- **详情与编辑分离：**详情只读；编辑保存时重新校验主体、分组、期次、IP、人员资格及配置版本。版本冲突提示重新载入，不覆盖他人已保存修改。取消编辑不得修改已生效配置。
- **变更边界：**改名称/分组仅改变运营展示；改IP/期次只影响后续归因；改名单/时段/方式/权重影响新分配，不自动批量改派已有负责人；改标签不追溯批量补写历史客户，补写需单独授权及任务记录。
- **启停与下载：**停用阻止新分配，不删除已建好友关系、不清空历史统计；恢复后使用最新有效配置。下载仅生成入口文件，不产生扫码或分配记录。不能声称停用即可使所有外部已下载静态码失效，实际拦截依赖入口控制和企微接口能力。
- **晚到回调：**停用或改配置后收到旧请求的真实成功事件，仍按原请求及原归因快照入账；无法唯一映射时保留证据转异常，不改用当前IP、当前员工伪造历史。
- **幂等与并发：**扫码/任务使用稳定请求ID；批量任务按任务ID＋线索ID记录结果。事件使用供应商事件标识或经接口验证的复合幂等键，不假设所有事件都自带统一事件编号。超时先查原结果，再决定补偿，禁止重复分配和重复加计。
- **标签失败：**加微成功后标签同步失败只重试标签动作，不撤销真实加微、不再次分配；内部标签与企微标签分别记录成功/失败状态。
- **数据权限：**查询、详情、编辑、启停、下载、重试分别鉴权；后台任务使用明确授权范围，不以浏览器当前选中主体代替请求主体。员工候选同时校验本主体映射与组织权限。
- **审计最小字段：**请求/任务ID、主体、活码、内部线索/客户ID（可空）、入口来源、规则与名单版本、候选及排除原因、时区与命中时间、算法、选中员工、前后负责人、分配结果、异常原因及事件追踪号。匿名身份不得使用手机号占位或虚构客户主键。

## 3. 共性实施约束

- 数据范围：页面列表、筛选、详情及导出均须受当前登录人的组织与数据权限约束；无权限的数据不得通过接口、地址参数或导出绕过。
- 写操作：新增、编辑、删除、绑定、分配、同步等写操作必须鉴权、校验、记录审计信息并保证接口幂等。
- 页面状态：须覆盖首次加载、加载中、无数据、筛选无结果、无权限、接口失败和部分外部平台失败等状态，并提供明确反馈或可重试入口。
- 数据留痕：业务记录原则上不做物理删除；关键状态变化、操作者、操作时间和变更前后值须可追溯。
- 外部依赖：企业微信、短信或第三方平台调用失败时，保留本地业务事实并记录失败原因，不得静默吞错或错误回滚已成功的本地事务。
- 历史口径：历史记录按发生时快照展示；配置后续变化不得反向改写历史业务结果。

## 4. 验收与回滚

- 功能验收：本模块各入口、筛选、列表、详情、弹窗、单条与批量操作均可按本文档规则完成闭环。
- 权限验收：不同角色、组织范围及无权限账号展示和可操作范围正确，越权请求被服务端拒绝。
- 异常验收：重复提交、并发修改、外部接口超时、空数据和失效数据均有确定结果与用户提示。
- 回滚要求：上线异常时可按功能开关或版本回退停用新增能力；回滚不得删除已产生的业务记录和审计记录。
